# Chess Outcome Predictor

Predicts the outcome of a chess game (white win / black win / draw) from
pre-game and early-game signals: player ratings, opening choice, time
control, and move count — trained on ~20,000 real Lichess games.

This project doubles as an end-to-end demo of a modern ML deployment
pipeline: a trained model served via a REST API, containerized with
Docker, deployed to Kubernetes, with automated builds via GitHub Actions.

## Architecture

```
Data (Lichess CSV)
  -> Model (scikit-learn RandomForest, saved as model.joblib)
    -> API (FastAPI, exposes POST /predict)
      -> Docker (packages the API into a portable container)
        -> Kubernetes (runs and self-heals the container via minikube)
          -> CI/CD (GitHub Actions rebuilds the image on every push)
```

## Results

- **Overall accuracy: 66%** on held-out test data (vs. ~33% for random guessing).
- The model performs well distinguishing white wins vs. black wins
  (precision/recall ~0.65-0.74) but **struggles to predict draws**
  (recall ~0.02), because draws make up less than 5% of the dataset.
  This is a textbook case of **class imbalance** — the model learned that
  rarely predicting "draw" is a safe statistical bet, even though it's not
  a useful one. Addressing this (e.g. class weighting, oversampling) is a
  natural next step.
- The single strongest feature is `rating_diff` (white rating minus black
  rating) — consistent with chess intuition that skill gap dominates outcome.

## Running locally (no Docker/Kubernetes)

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

python train.py          # trains the model, saves model.joblib
uvicorn app:app --reload # starts the API on http://127.0.0.1:8000
```

Visit `http://127.0.0.1:8000/docs` for interactive API docs.

## Running with Docker

```bash
docker build -t chess-predictor .
docker run -p 8000:8000 chess-predictor
```

## Running with Kubernetes (minikube)

```bash
minikube start --memory=2200 --cpus=2
minikube image load chess-predictor:latest

kubectl apply -f deployment.yaml
kubectl apply -f service.yaml

kubectl get pods                     # confirm it's Running
minikube service chess-predictor-service   # opens it in your browser
```

## Example request

```bash
curl -X POST http://127.0.0.1:8000/predict \
  -H "Content-Type: application/json" \
  -d '{
    "white_rating": 1800,
    "black_rating": 1500,
    "opening_name": "Sicilian Defense",
    "base_time": 10,
    "increment": 5,
    "turns": 40
  }'
```

Response:

```json
{
  "predicted_winner": "white",
  "probabilities": { "white": 0.62, "black": 0.35, "draw": 0.03 }
}
```

## What I learned

- Feature engineering (rating difference, parsing time controls, bucketing
  rare categories) mattered more to model quality than model choice itself.
- Class imbalance is a real, common failure mode — high overall accuracy
  can hide a model that's nearly blind to a minority class.
- Docker images need their own consistent Python/library versions,
  independent of the host machine — pinned dependencies from one Python
  version can silently fail to install on a container using a different one.
- Kubernetes's declarative model (describe desired state, let the
  system enforce it) is what enables self-healing — killing a Pod
  manually and watching it get recreated automatically was the clearest
  illustration of this.

## Possible next steps

- Address class imbalance for draw prediction (class weighting, SMOTE).
- Add a lightweight frontend for non-technical users to try predictions.
- Deploy the Kubernetes manifests to a real cloud cluster (e.g. a free-tier
  GKE/EKS cluster) instead of only locally via minikube.
- Add automated tests and have CI run them before building the image.
